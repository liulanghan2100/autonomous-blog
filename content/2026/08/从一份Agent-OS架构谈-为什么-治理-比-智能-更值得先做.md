# 从一份Agent OS架构谈：为什么"治理"比"智能"更值得先做

> 当别人在卷 Agent 的能力上限时，有人把"边界"设计成了整个系统的地基。

## 开头：我为什么觉得这份架构有意思

这两年 Agent 圈子的叙事几乎没变过：多智能体编排、工具调用、RAG、记忆增强……大家都在往"更聪明"的方向狂奔。但我身边真实落地项目的结局往往不是"不够聪明"，而是**不可控**——Agent 乱调接口、绕过审批、把没验证的结果当结论写进系统、花掉超预算的 token。

所以我看到这份 **Agent OS Core 分层架构**时，第一反应是：这作者把问题看反了。它没把重点放在"Agent 多聪明"，而是把**"治理"放到了第 0 层**——所有上层建筑都绕着它转。

## 一、最反直觉的设计：治理宪法在最底层

架构图第一层不是"能力"而是 `Governance Constitution / 治理宪法层`，包含 7 个门禁、主人审批门、证据规则、审计、回滚、反作弊、成本边界、权限边界。

翻译成人话，就是**系统在动手之前先立了规矩**：

- **没有证据不算完成**：调研、测试、运行结果必须落盘。这条直接堵死了 Agent 最常见的恶习——"我觉得可以了"。
- **反作弊**：防止 benchmark 泄漏、伪造搜索、伪造验证、事后补证据。看到这条我笑了，因为这真的是 Agent 会干的事。
- **成本边界**：禁止无审批调用真实付费接口。这是"自给自足"Agent 的命门。

用代码理解它的强制力，大概是这样：

```python
class Gate:
    def __init__(self, name, policy):
        self.name = name
        self.policy = policy

    def check(self, action):
        # 所有动作必须先过门禁，门禁是系统级钩子，Agent 无法绕过
        if not self.policy.approve(action):
            raise PermissionError(f"action blocked by {self.name}")
        log_audit(action)  # 审计，任何操作留痕
        return action
```

核心点在于：**门禁不是 Agent 自己写的，是系统层强制注入的**。这跟很多团队"靠 prompt 约束 Agent 别乱来"的做法有本质区别——prompt 是建议，门禁是强制。

## 二、七个 Agent 只是"门面"：能力不归 Agent 私有

第二层 `7 Agent Facade Layer` 有个很清醒的设计：**保留 7 个 Agent（战略/设计/数据/计划/开发/QA/运维），但它们只是角色入口和任务分发，不私自堆能力**。

这解决了多 Agent 系统里一个非常常见的腐化问题：每个 Agent 都往自己身上挂工具、挂记忆、挂 prompt，最后变成 7 个各怀私货的"军阀"。这里的做法是把能力上收：

- **Skill 实体库**统一存放所有 SKILL.md、scripts、references
- **Skill 注册表**记录名称、版本、状态、风险等级、依赖
- **Skill 路由器**根据任务、角色、风险、历史成功率选 Skill
- **Skill 使用证据**记录"装没装、用没用、有没有贡献、失败原因"

妙处在于"使用证据"——Skill 好不好用不再靠嘴说，而是靠数据：**哪些 Skill 在什么任务里真的贡献了结果**。这是 Skill 能进化的前提。

## 三、吸收外部项目的方式：隔离研究，而非直接吞并

架构里 `Lab Archive / 实验归档层` 是我最喜欢的部分。它把一大串外部项目列成"研究对象"：

- **Omnigent** → 多 Agent 控制平面机制
- **Better Harness** → 能力使用证据机制
- **Firecrawl** → 网页抓取、搜索证据采集
- **Cognee** → 记忆/知识图谱
- **GAIA** → 评测实验（**只评测，不反向污染知识库**）

这种"吸收机制、隔离实体"的做法，避免了两个经典翻车现场：

1. 直接把别人的框架塞进核心 → 架构被绑架
2. 把未验证的"先进能力"接入生产 → benchmark 污染、行为失控

对照我自己踩过的坑：曾经为了一个"看起来很酷"的 RAG 库，直接把整个检索链路换掉，结果线上召回质量一落千丈，回滚花了两天。**正确的姿势就应该是这种：先在 Lab 里跑通、沉淀机制，再进核心。**

## 四、故障自复位：Agent 也要有"免疫力"

第 5 层 `Failure Recovery` 定义了完整的自复位链路：

```
检测 → 分类（临时/配置/权限/provider/治理违规）
     → 重试策略（可重试自动重试，不可重试升级）
     → 降级路由（只切到已批准备用方案）
     → 检查点 + 回滚
     → 故障报告 + 经验沉淀（回流到记忆和知识库）
```

最有价值的是最后一步：**每次失败沉淀成可复盘材料，回流到 Memory 和 Skill Usage Evidence**。这意味着系统会越来越"懂"自己的故障——第一次踩坑是事故，第二次就是预期管理。

## 五、我的三点保留意见

这份架构已经很完整，但纸上谈兵总有盲区：

1. **七层 Agent 门面会不会变成流程官僚**？审批、证据、门禁全部强制后，简单任务也可能被拖成"填表"。建议分层：低风险任务走快速通道，重流程只用于高风险操作。
2. **"治理宪法不可修改"本身是个隐患**。宪法要是永远改不了，等系统能力进化后，过时规则会变成枷锁。需要有"宪法修正案"机制，且修正必须有人工参与。
3. **真实落地的成本**：这架构需要的证据服务、审计、检查点、回滚全都要真实存储和基建支撑，小团队要掂量值不值。我的建议是**只先落地三个**：证据规则、成本边界、回滚。

## 总结

这份 Agent OS 架构给我的最大启发不是某个具体模块，而是一个**优先级判断**：在 Agent 能力越来越强的今天，"让它遵守规则"比"让它更聪明"更稀缺，也更重要。

聪明的 Agent 满大街都是，**可治理的 Agent 才是能进生产环境的 Agent**。如果你也在搭自己的 Agent 系统，我建议先画一版"治理宪法"，再谈能力。
